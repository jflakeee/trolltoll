## 1. Overview

The browser stores player position, stats, equipment flags, resources, boss clears and progression in `localStorage`. The primary key is `trolltoll_web_v3`; a legacy mirror is written to `trolltoll_web_v2`. On startup, a structurally valid v3 record takes precedence, otherwise the game falls back to v2 or v1. The separate pure module implements stricter normalization/migration and is not invoked by the browser runtime.

## 2. Detailed Design

- Browser load: parse v3; require `schemaVersion===3` and an object `legacy`. If invalid or unavailable, load v2/v1. If parsing throws, retry legacy and ultimately initialize defaults.
- `p` holds live legacy fields including position, level, XP, base attack/defense, HP, kill count, materials, equipment/facilities and boss IDs. `progression` holds inventory, weapon enhancement and reward pity.
- Browser save writes v3 `{schemaVersion:3,revision:0,legacy,progression}` and then the v2 legacy mirror. No transactional/atomic write spans the two keys.
- Save triggers: every 5 seconds, `pagehide`, document hidden, enemy kill, gather completion, craft/build actions and enhancement attempts.
- Browser errors in save set `storageWarning=true`; `SecurityError`/`QuotaExceededError` on load also trigger the warning.
- Pure module `migrateSave` supports schema 1, 2, 3 and no-version legacy objects; it sanitizes nonnegative integer counters, boss IDs, equipment levels 0–15 and failure-counter keys 0–14. `decodeSave`/`encodeSave` are JSON adapters.

## 4. Edge Cases and Dependencies

**Handled:** absent data defaults; v3 with invalid legacy structure falls back; browser clamps invalid enhancement counters and boss IDs; pure module rejects unsupported schema versions and invalid v3 legacy structures.

**Risks:** browser loader does not call `migrateSave` and may interpret a malformed but structurally valid v3 differently from the pure module. A valid JSON v3 with `legacy` object can bypass stricter normalization. Writes to v3 and v2 are non-atomic, and v2 cannot preserve enhancement/progression inventory. Browser saves do not use `revision` to detect stale data.

**Dependencies:** all persistent gameplay systems; browser storage availability; versioned state contracts. **INTENT UNKNOWN:** Should corrupt v3 automatically fall back to v2, or surface recovery options? Is the v2 mirror intended for long-term compatibility?

## 6. Review Remediation — Recovery Contract (proposed, NOT implemented)

**Current behavior (do not misrepresent as protection):** v3 is written first and the v2 mirror second; a successful v3 write followed by a failed v2 write leaves a valid newer v3 and an older mirror. A failed v3 write can leave the old v3 intact; the loader may fall back to v2/v1 if v3 is invalid. v2 cannot restore enhancement stones, equipment level, or reward pity. A parseable v3 object with malformed nested progression can be accepted by the browser loader. No atomic commit, verified backup, monotonic revision, or rollback mechanism currently exists.

**Proposed future policy (requires explicit approval and implementation):**
1. Preserve the existing v3 key and legacy keys throughout migration; never delete or overwrite a last-known-good v3 solely because v2 exists.
2. Before any new save strategy ships, introduce a separate full-fidelity v3 backup key. Validate a snapshot's complete progression and legacy data before considering it recoverable; do not describe the existing v2 mirror as a full backup.
3. On read, prefer a validated primary v3; if invalid, attempt validated full-fidelity backup; only then offer legacy fallback with a clear warning that enhancement/progression may be lost. Never silently replace corrupted v3 with a newly initialized save during recovery.
4. If storage is unavailable or quota-exceeded, preserve the in-memory game state, expose a persistent warning, and do not claim persistence. Do not clear existing keys as an automatic quota remedy.
5. If a revision scheme is introduced, make it monotonic per committed snapshot and define how a partially written candidate is rejected; the current fixed `revision:0` must not be interpreted as ordering.
6. Add a migration test matrix: valid v3; malformed JSON v3; valid JSON with malformed `legacy`; malformed nested `progression`; v3 write succeeds/v2 write fails; v3 write fails; both keys absent; storage throws on read/write; v2-only migration; v3 with nonzero enhancement. For each case assert selected source, retained progression, warning, and whether any key changed.

**Review gate:** This document specifies the failure modes and an approval-dependent recovery contract, **not** a completed P0 runtime fix. Implement the policy and prove non-destructive migration before treating save-loss risk as resolved. Real-browser reload/background tests remain open.

**Provenance:** observed behavior only; recovery policy remains unapproved.

## 7. P0 Implementation Update (2026-11-11)

The browser now uses `trolltoll_web_v3_backup` as a **full-fidelity recovery copy**. A save writes the complete v3 snapshot to backup, then primary, then the legacy v2 mirror. Snapshots carry monotonically increasing revisions for the current session; on load, the valid snapshot with the larger revision wins. A corrupt primary recovers from a valid backup without resetting enhancement. If both full-fidelity copies exist but are invalid, legacy data can be displayed but saving is blocked to avoid overwriting damaged v3 data. Storage access failures also block writes; all failures set a warning. A failed v2 mirror write no longer invalidates the successful full v3 save.

**Compatibility:** Existing v3 saves without a backup still load; v2-only saves can migrate on the next successful save. Early v3 records without `progression` remain readable. No old storage keys are deleted. Validation checks the nested progression shape and nonnegative counters before using it as a recovery source.

**Verified in CI:** `tests/save-recovery.cjs` injects malformed JSON, invalid nested progression, newer backup after partial primary failure, failed backup/primary/mirror writes, legacy-only migration, storage denial, and empty storage. `tests/browser-v3.cjs` checks recovery of enhancement after corrupt primary. **Not yet verified:** actual Android background/restart, browser quota eviction, interrupted writes across tabs, or a user-facing export/recovery UI. The previous proposed recovery contract remains a design reference; this section records the implemented subset. **Review:** pending independent re-review.
